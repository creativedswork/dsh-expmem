# DSH ExpMem 0.3.0 implementation plan

Status: implementation-ready plan

Target: `@creative-dswork/dsh-expmem@0.3.0`

Design discussion: [Issue #1](https://github.com/creativedswork/dsh-expmem/issues/1)

## Goal

`0.3.0` adds a trustworthy lifecycle to file-backed experience memory:

- every record states its trust status and provenance;
- imported and agent-generated records start as candidates;
- verification requires evidence that can be inspected later;
- conflicts and supersession preserve the earlier records;
- legacy `0.2.x` files remain readable without a bulk migration;
- deletion keeps a minimal tombstone while avoiding a full audit platform.

ExpMem continues to own memory storage, retrieval, lifecycle, and migration. External audit
systems may produce review reports, but ExpMem stores only opaque report references. It does not
scan or parse report directories, run review models, dereference report locations, or treat report
verdicts as truth.

## Current baseline

The implementation starts from these verified facts:

| Area | Current behavior | Consequence for 0.3.0 |
|---|---|---|
| Archive format | One JSON file per record under `archive/<kind>/<uuid>.json` | Version handling must operate per file, not per JSONL row. |
| Legacy marker | Records contain `version: 1` | Treat this shape as legacy v0; the formal schema starts at `schemaVersion: 1`. |
| Time | `createdAt` and `updatedAt` use `Date.now()` | New time fields remain Unix epoch milliseconds. |
| Writes | Temporary file plus atomic rename | Reuse this for records and tombstones. |
| Search | Literal case-insensitive AND over a linear scan | Keep the scan; add status and evidence projection without an index. |
| Import | Provider and absolute path identify an imported source; SHA-256 detects changes | Convert this provenance to evidence while retaining idempotence. |
| Agent tools | `expmem_search`, `expmem_write`, `expmem_forget` | Add one focused lifecycle tool instead of overloading content writes. |
| CLI | Import only | Add confirmed deletion; keep Node standard library parsing and prompts. |
| Promotion | A 70% pressure notice asks the current Agent to write durable knowledge | Promotion creates candidates unless qualifying evidence is supplied. |
| Tests | Three Node test cases plus packed-install verification | Extend the existing runner; add no test framework. |

Baseline verification:

```sh
pnpm run check
```

passes three tests on `main` at `ea4ab96`.

## Scope

### Included

- formal `schemaVersion: 1`;
- `candidate`, `verified`, `disputed`, and `superseded`;
- authorship, claimed time, evidence, and verification metadata;
- record-level conflicts;
- single-authority supersession edges;
- per-file legacy normalization and unsupported-version diagnostics;
- status-aware search and prompts;
- candidate-safe import updates;
- confirmed deletion and minimal tombstones;
- an opaque `review-report@1` reference contract;
- focused audit fixtures for loader diagnostics, atomic record recovery, guarded verification,
  and tombstones;
- bilingual documentation and packed-install coverage.

### Excluded

- model SDKs, API keys, or execution of an external review pipeline;
- scanning, loading, parsing, or validating the contents of external report directories;
- automatic fact checking or confidence scores;
- field-level conflict tracking;
- immutable mutation journals or compliance reports;
- semantic search, embeddings, and automatic conflict detection;
- a database or a new background process;
- an approval workflow beyond one local CLI confirmation.

## Storage contract

### Formal record schema

Move the storage types and validation helpers into `src/schema.ts`. Keep filesystem operations in
`src/storage.ts`.

```ts
export type ExperienceKind = 'habit' | 'experience' | 'insight'

export type MemoryStatus =
  | 'candidate'
  | 'verified'
  | 'disputed'
  | 'superseded'

export interface MemoryActor {
  kind: 'user' | 'agent' | 'tool'
  id?: string
}

export type MemoryEvidence =
  | {
      id: string
      kind: 'session-event'
      sessionId: string
      startSeq?: number
      endSeq?: number
      observedAt: number
    }
  | {
      id: string
      kind: 'imported-file'
      provider: 'claude' | 'codex'
      path: string
      sha256: string
      observedAt: number
    }
  | {
      id: string
      kind: 'external-uri'
      uri: string
      capturedTextSha256?: string
      observedAt: number
    }
  | {
      id: string
      kind: 'review-report'
      schemaVersion: 'review-report@1'
      reportId: string
      location: string
      sha256: string
      targetSha256: string
      observedAt: number
    }

export interface MemoryVerification {
  actor: MemoryActor
  method: 'user-confirmation' | 'tool-reproduction' | 'source-check'
  evidenceIds: string[]
  verifiedAt: number
}

export interface ExperienceMemory {
  schemaVersion: 1
  id: string
  kind: ExperienceKind
  title: string
  content: string
  tags: string[]
  status: MemoryStatus
  authoredBy: MemoryActor
  evidence: MemoryEvidence[]
  evidenceText?: string
  createdAt: number
  updatedAt: number
  claimedAt?: number
  workspace?: string
  verification?: MemoryVerification
  supersedes?: string[]
  conflictsWith?: string[]
}
```

The new writer stops emitting legacy `version`, `sourceSession`, and `importedFrom`. The v1
projection exposes their information through `schemaVersion`, `authoredBy`, and `evidence`.

`review-report` is a link to an externally owned artifact:

- `schemaVersion` identifies the external report contract independently of the memory schema;
- `reportId` is the external pipeline's stable report identifier;
- `location` is the path or URI used by a user or external tool to find the report;
- `sha256` identifies the exact report bytes;
- `targetSha256` identifies the exact ExpMem claim version reviewed.

ExpMem validates this link object but does not open `location`, recompute the report hash, inspect
`verdict`, or import fields such as `reviewers` and `evidenceHashes`. The external producer owns
report availability and report-file validation.

Add a public `claimSha256(memory)` helper. It hashes the UTF-8 bytes of `JSON.stringify()` over a
new object with this fixed property order:

```ts
{
  kind: memory.kind,
  title: memory.title,
  content: memory.content,
  claimedAt: memory.claimedAt ?? null,
}
```

The digest format is `sha256:<64 lowercase hexadecimal characters>`. Tags, workspace, status,
authorship, evidence, verification, relations, and storage timestamps are excluded so metadata
changes do not invalidate a review of unchanged claim text. A newly attached review report must
target the resulting digest. A candidate claim update revalidates retained report links; the
caller must remove or replace a link that targets the earlier claim.

### Evidence rules

- Evidence IDs are UUIDs generated by ExpMem when omitted from a write request.
- All v1 hash fields must match `sha256:<64 lowercase hexadecimal characters>`.
- `evidenceText` is human-readable context only and never verifies a claim.
- `startSeq` and `endSeq` must either both exist or both be absent.
- A Session reference without an event range records provenance but cannot verify a claim.
- `imported-file` proves which bytes were imported; it does not prove their claim.
- `review-report` requires a non-empty `reportId` and `location`, and its `targetSha256` must match
  the current claim digest when the link is attached or retained.
- `review-report` records that a specific report targets a specific claim version; neither the
  report nor its verdict can satisfy verification by itself.
- `verified` requires a `verification` object whose IDs exist in the record.
- `user-confirmation` requires a user actor and a complete Session event range.
- `tool-reproduction` requires a tool actor and a complete Session event range.
- `source-check` requires an external URI reference.
- `imported-file`, `review-report`, weak Session references, and `evidenceText` cannot verify a
  claim by themselves.
- `claimedAt` describes the time asserted by the claim. It is not evidence.
- All time values are safe integer Unix epoch milliseconds.

The implementation does not score evidence or infer whether a source is independent.

### Legacy normalization

The loader classifies each JSON file independently:

| Input | Result |
|---|---|
| `schemaVersion === 1` | Validate and return v1. |
| No `schemaVersion`, valid current `version === 1` shape | Normalize to v1 candidate in memory. |
| `schemaVersion > 1` | Skip during scans and report `unsupported-schema`; reject direct updates. |
| Invalid JSON | Skip during scans and report `invalid-json`; reject direct updates. |
| Invalid known schema | Skip during scans and report `invalid-record`; reject direct updates. |

Legacy conversion:

- `status` becomes `candidate`;
- `version` is removed from the normalized value;
- `importedFrom` becomes one `imported-file` evidence item with `observedAt = createdAt`; its
  legacy bare hexadecimal digest is normalized to the v1 `sha256:<digest>` format;
- `sourceSession` becomes a Session evidence item without an event range;
- imported records use `authoredBy: { kind: "agent", id: provider }`;
- other records use the source Session ID as the Agent ID when available;
- `claimedAt`, `verification`, `supersedes`, and `conflictsWith` remain absent.

Search and list do not rewrite files. The next successful update writes the normalized v1 shape.
This avoids a package-install migration and preserves rollback access to untouched files.

### Scan diagnostics

Add:

```ts
export interface ArchiveWarning {
  path: string
  code: 'invalid-json' | 'invalid-record' | 'unsupported-schema'
  message: string
}

export interface ArchiveScanResult {
  memories: ExperienceMemory[]
  warnings: ArchiveWarning[]
}
```

`scan()` continues past bad files. `read(kind, id)` remains strict because a requested mutation
must not silently target an unreadable record. Search returns warnings with its page; the importer
includes them in machine-readable output.

### Atomic write recovery

Keep one temporary file and one rename per record or tombstone. Temporary files remain in the
target directory and retain the existing `.<uuid>.tmp` naming pattern.

- Scans read only final `.json` files and never promote temporary contents.
- An interrupted replacement therefore leaves either the earlier committed JSON file or the new
  committed JSON file visible, never a partial JSON record.
- An interrupted first write leaves no visible record.
- Orphaned temporary files remain inert and do not block later writes because each write uses a
  new random temporary name.
- Recovery never interprets the temporary file or guesses its intended target.

This contract covers process interruption and atomic visibility on the supported local
filesystems. It does not claim power-loss durability because `0.3.0` does not add file and
directory `fsync`. It also does not add startup cleanup: deleting apparent orphan files could race
with another live ExpMem process.

### Tombstones

Store tombstones at:

```text
archive/tombstones/<uuid>.json
```

```ts
export interface MemoryTombstone {
  schemaVersion: 1
  id: string
  kind: ExperienceKind
  deletedAt: number
  reasonCode: 'user-request' | 'duplicate' | 'incorrect' | 'privacy'
}
```

Tombstones contain no title, content, tags, workspace, author, or evidence. Existing relations may
refer to a tombstoned ID so that deletion does not require rewriting unrelated files. New
relations cannot target a tombstone.

## Lifecycle

### State transitions

Persisted transitions:

```text
candidate -> verified
candidate -> disputed
verified  -> disputed
```

Conflict resolution creates a new verified record that supersedes the disputed records. ExpMem
does not rewrite a disputed claim into a new fact.

`superseded` is terminal. A verified record declares the authoritative `supersedes` edge. The
loader computes `supersededBy` as a read-time projection and treats the target as superseded even
if a crash prevented its denormalized status field from being updated.

### Content mutability

- Candidate records may change title, content, tags, claimed time, evidence, and evidence text.
- Verified and disputed records keep their claim text unchanged.
- Verified and disputed records may receive additional evidence, evidence text, or relation
  metadata.
- Superseded records reject all updates.
- Corrections create a new candidate and later supersede the earlier record.

This rule preserves the claim that was originally verified or disputed without adding a revision
journal.

### Supersession rules

- Only a verified record may declare `supersedes`.
- Targets must exist as live records when the relation is created.
- A record cannot supersede itself.
- The directed graph must remain acyclic.
- A target may have at most one incoming supersession edge.
- `supersedes` is the persisted authority; `supersededBy` is never stored.

The write path validates the complete in-memory graph before writing the source record. It then
updates target status files as a convenience. A subsequent scan derives the correct effective
status from the authoritative edge if a process stops between those writes.

### Conflict rules

- `conflictsWith` is record-level in `0.3.0`.
- Targets must exist and cannot be the source record.
- A record declaring conflicts must be disputed.
- Readers treat the relation as symmetric even if only the declaring side stores the edge.
- A superseded record takes precedence over disputed when resolving effective status.
- ExpMem does not detect conflicts automatically.

## Runtime API

### `FileExperienceArchive`

Keep the class and atomic JSON writer. Add only the methods required by the lifecycle:

```ts
scan(): Promise<ArchiveScanResult>
readRecord(kind, id): Promise<ExperienceMemory>
writeCandidate(input, source): Promise<ExperienceMemory>
transition(input, source): Promise<ExperienceMemory>
forgetCandidate(kind, id, reasonCode): Promise<MemoryTombstone>
forgetConfirmed(kind, id, reasonCode): Promise<MemoryTombstone>
search(options): Promise<ExperienceSearchPage>
```

`writeCandidate` replaces the current create/update path:

- create defaults to candidate;
- update is allowed only while the effective status is candidate;
- runtime writes default `authoredBy` to the calling DSH Agent and Session;
- a write claiming user authorship must include a complete Session event range;
- runtime writes automatically add weak Session provenance if a source Session exists;
- duplicate evidence IDs and identical imported-file evidence are removed.

`transition` owns verification and relation validation. It prevents lifecycle rules from being
spread across tool handlers, the importer, and the CLI.

`claimSha256` is used by candidate writes and transitions that attach or retain a review report.
It does not read the report file or make the report qualifying verification evidence.

### Search

Extend search options:

```ts
statuses?: MemoryStatus[]
```

Default search returns candidate, verified, and disputed records. Superseded records require an
explicit status filter. Each hit adds:

- effective `status`;
- `authoredBy`;
- evidence kinds and references;
- verification method when present;
- `supersedes`, derived `supersededBy`, and resolved conflicts.

For review-report evidence, the projection returns `schemaVersion`, `reportId`, `location`,
`sha256`, `targetSha256`, and whether the target hash matches the current claim. It never returns
or infers an external verdict.

The existing literal AND matching and cursor behavior remain unchanged.

### Agent tools

Keep:

- `expmem_search`;
- `expmem_write`;
- `expmem_forget`.

Add:

- `expmem_transition`.

`expmem_write` creates or updates candidates. It accepts authorship, claimed time, and evidence,
including human-readable evidence text, but does not set verified, disputed, or superseded.
If the caller omits authorship, ExpMem records the calling Agent and Session.
Review-report evidence is accepted only when its target hash matches the resulting candidate
claim.

`expmem_transition` accepts:

- exact category and ID;
- target status, limited to verified or disputed;
- evidence to append;
- verification metadata for verified;
- human-readable evidence text;
- `supersedes` for verified;
- `conflictsWith` for disputed.

The tool uses the schema DSL's supported nested objects and exact-one `oneOf` branches for
evidence variants. Runtime validation still enforces cross-field rules.

`expmem_forget` deletes only effective candidate records and writes a tombstone. For any other
status it returns an error with the corresponding CLI command. Its reason code defaults to
`user-request`.

### Prompt and pressure promotion

Replace the current instruction to write only verified knowledge:

- stable but unverified experience may be stored as candidate;
- the Agent must not present candidate or disputed memory as fact;
- verification requires cited evidence;
- review reports cannot verify a record;
- review report locations are external references and are not opened by ExpMem;
- search before creating or transitioning;
- pressure promotion defaults to candidate.

The pressure and recovery hooks retain their current thresholds and once-per-compaction behavior.
Only their messages change. No additional model call is added.

## Import behavior

Replace `importedFrom` lookup with the normalized `imported-file` evidence.

For each source path:

| Existing record | Source hash | Action |
|---|---|---|
| None | Any | Create candidate. |
| Candidate | Same | Skip. |
| Candidate | Changed | Update the same candidate and evidence hash. |
| Verified/disputed/superseded | Same | Skip. |
| Verified/disputed/superseded | Changed | Create a new candidate; retain the earlier record. |

When several records refer to one provider/path, the importer chooses the newest evidence
observation as the current source revision. It does not create a supersession edge automatically.
After the new candidate is verified, the Agent or user may supersede the older record.

Importer-created records use:

```ts
authoredBy: { kind: 'agent', id: 'claude' | 'codex' }
status: 'candidate'
```

Dry-run output reports whether a changed source would update a candidate or create a new candidate
beside a protected record.

## CLI deletion

Extend the standard-library CLI:

```text
dsh-expmem forget <habit|experience|insight> <uuid>
  --root-dir <path>
  --reason-code <user-request|duplicate|incorrect|privacy>
  --yes
  --json
```

Behavior:

1. read and display ID, kind, status, and title;
2. require an interactive confirmation unless `--yes` is present;
3. reject invalid and unsupported records;
4. delete the record with `forgetConfirmed`;
5. atomically write the minimal tombstone;
6. print the tombstone path and deleted status.

Use `node:readline/promises`; add no CLI dependency. The package test supplies stdin for the
interactive path and separately covers `--yes`.

## Risks and controls

| Risk | Control |
|---|---|
| The old `version: 1` looks like a formal schema version | Detect the exact legacy shape before checking `schemaVersion`; document the distinction. |
| One corrupt file breaks all memory search | Scan per file and return warnings; keep exact record mutation strict. |
| An interrupted write leaves a partial visible record | Scan only final JSON files; leave temporary files inert to avoid racing another live writer. |
| A process stops during a multi-record relation update | Treat the source edge as authority and recompute effective status on every scan. |
| Imported verified content changes upstream | Create a new candidate instead of overwriting the verified claim. |
| A report is linked to the wrong claim revision | Canonically hash claim fields and require `targetSha256` to match when the link is attached or retained. |
| A report hash or verdict is mistaken for factual proof | Treat the report as opaque, do not dereference it, and reject verification backed only by `review-report`. |
| External fixtures expand ExpMem into an audit platform | Accept only fx-04, fx-05, fx-07, and fx-08 under `tests/fixtures/audit/`. |
| Tombstones leak deleted content | Permit only ID, kind, deletion time, and enum reason. |
| Tool input becomes difficult for the Agent | Keep content writes and lifecycle transitions separate; use one new tool only. |
| The feature grows into an audit platform | Keep reviewers, model execution, scoring, reports, and policy engines outside the package. |

## Definition of done

`0.3.0` is ready when:

- all planned record states are reachable through documented operations;
- every verified record has qualifying evidence;
- every stored review-report link identifies a report location, report bytes, and the exact claim
  digest while remaining non-verifying evidence;
- valid records remain searchable beside legacy, corrupt, and future-version files;
- conflicts and supersession never destroy the earlier claim;
